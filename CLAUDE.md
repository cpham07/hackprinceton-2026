# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

HackPrinceton 2026 hackathon project. There is no linter or test suite.

## Commands

- Backend: `cd backend && python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt && cp .env.example .env && uvicorn main:app --reload` (port 8000, `GET /health`, API docs at `/docs`; set `OPENAI_API_KEY` in `backend/.env` for the AI routes). Tests: `pip install -r requirements-dev.txt && pytest` (no network). See `backend/README.md`.
- Frontend: `cd frontend && npm install && npm run dev` (port 5173). `npm run build` type-checks and builds; `npm test` runs the Vitest unit tests (`src/**/*.test.ts`, no network). In dev only, `http://localhost:5173/?chapter=5` starts the final chapter with Chapter 4 complete, `?chapter=4` starts Chapter 4 outside Zeus's palace with Chapter 3 complete and the bolt in hand, `?chapter=3` starts inside Zeus's palace with Chapter 2 already complete (all seals), and `?chapter=2` starts in the Chapter 2 hub with Chapter 1 already complete; add `&seals=athena,ares,hades` (or `&seals=all`) to start with seals already earned (`game/devShortcuts.ts`).

## Architecture

- `frontend/`: Vite + React 18 + TypeScript + Phaser 3. Game logic lives in Phaser (`src/game/`), UI in React (`src/components/`).
  - `App.tsx` owns the open dialogue session, the open puzzle, and the single `submitPlayerResponse(PlayerResponse)` handler (typed text now, voice transcriptions later).
  - `components/`: `GameCanvas` (creates/destroys the Phaser game), `DialogueBox` (`hideInput` gives a read-only mode), `SymbolPuzzle`, `ChallengeComplete` (success overlay after a trial), `SealToast` (announces each new seal), `QuestTracker` (Chapter 1 clues or Chapter 2 seals, by `state.chapter`), `ClueToast`, `ChapterComplete` (takes an explicit `completedChapter` prop, 1 to 4; each calls `onContinue` to start the next chapter's scene; `EndingScreen` is the final screen after Chapter 5, whose only action restarts the game; never infer it from `state.chapter`, which has already moved on). `hooks/useGameState.ts` subscribes React to the story state.
  - `game/EventBus.ts` is the only Phaser/React channel. Phaser to React: `dialogue:request`, `puzzle:request`, `scene:ready`, `challenge:complete`. React to Phaser: `overlay:opened` / `overlay:closed` (one input lock for every blocking overlay; `App` emits them when "any overlay open" changes) and `scene:start` (scene change; keys are `SCENES` in `game/constants.ts`).
  - `game/scenes/GameplayScene.ts` is the base class for playable scenes: player, keys, `InteractionManager`, the overlay input lock, `scene:start` handling and shutdown cleanup. Scenes call `initGameplay()` in `create()`, `tickGameplay()` in `update()` and `addCleanup()` for their own subscriptions. `OlympusEntrance` (Chapter 1), `OlympusHub` (Chapter 2; Athena's library is the enclosed far end of the same scene) `AresTraining` (Ares's arena) and `HadesChamber` extend it. Scenes change with `goToScene(key)`; override `sceneStartData(key)` to pass transient data such as a spawn point (`OlympusHub.init()` reads `spawnX`). Never put spawn points in the story state.
  - An interactable can handle E itself through `onInteract` (return true when handled), e.g. portals and the palace gates; returning false falls back to its dialogue. `Npc.prompt` is mutable so a scene can change it with the story state.
  - Chapter 2 ends in the hub: `completeChapter2IfReady()` (`story/chapter2.ts`) checks `hasAllSeals` and applies `CHAPTER_2_COMPLETE_ACTIONS` (sets chapter 3). It is called only when the player presses E at the unlocked palace, never automatically when the third seal is granted. Its completion screen continues into the `ZeusPalace` scene (Chapter 3). After that, E at the hub palace gates walks straight in.
  - `entities/Hazard.ts`: vertically oscillating hazard (tweened, gravity-free, immovable dynamic body with `setDirectControl(true)`); sizes and timing come from config.
  - Chapter changes are explicit: the completion screen emits `scene:start`. Never switch scenes just because `state.chapter` changed.
  - `game/state/gameState.ts` is the authoritative story state (plain TS module: `getGameState`, `subscribe`, flags, clues, quests, seals, inventory via `addItem`/`hasItem`, and numeric `counters` such as puzzle statue positions). Don't keep story state in the Phaser registry.
  - `game/input/keys.ts` creates gameplay keys and holds the explicit list of captured keys. The scene releases captures and disables the keyboard while dialogue is open. Use `consumePress` for one-shot actions, not `JustDown` (it misses taps shorter than a frame).
  - `entities/Player.ts`, `entities/Npc.ts`, `systems/InteractionManager.ts` are reusable across scenes.
  - `game/data/interactables.ts` defines every NPC and object the player can press E on, grouped per scene (position, display size, interaction radius, prompt text, optional glow, `kind: "puzzle"` to open a puzzle instead of a dialogue). `entities/Npc.ts` builds any of them.
  - Story progress only changes through `story/actions.ts` (`applyStoryActions` with `setFlag` / `addClue` / `completeQuest` / `grantSeal` / `setChapter`). Dialogue steps carry actions that apply when the line is shown, never just because a dialogue opened.
  - `story/chapter1.ts` and `story/chapter2.ts` hold each chapter's flags, data (clues, seals) and objective function; `story/chapter1Dialogue.ts` and `story/chapter2Dialogue.ts` pick each character's conversation from the current state, and `story/conversations.ts` is the lookup by interactable id.
  - `puzzles/sequencePuzzle.ts` (type, `isCorrectSequence`, `shuffledStart`) and `puzzles/wisdomPuzzle.ts` (symbols, solution, reward actions). Whether a puzzle is solved is read from game state, not kept in the component.
  - `dialogue/conversation.ts` is the scripted reply engine (`getReply`); `dialogue/phraseMatch.ts` is the deterministic phrase validator used for the incantation.
  - Scenes mirror story state via `subscribe()` + `applyStoryState()` (gate and library door art, barrier collision, sleeping gatekeeper, seal emblem). Don't copy story state into a scene.
  - `game/graphics/placeholders.ts` generates placeholder textures under fixed keys and never overwrites a key that real art already loaded, so a missing or failed file falls back to its placeholder. Display sizes and collision boxes come from `PLAYER_CONFIG` and the NPC definitions, not from texture dimensions.
  - NPC art (`frontend/public/assets/characters/npcs/`: Zeus, Athena, Aphrodite as PNG; Ares and Hades as hand-authored SVGs, loaded with `load.svg` at the frame size) is listed in `game/graphics/characterArt.ts` (`CHARACTER_ART`, keyed by the interactable's `textureKey`): source-pixel crop, feet line, anchor between the feet and a `worldHeight`. `GameplayScene.preload()` loads it for every scene; `Npc` (a Sprite) scales it uniformly, so the per-scene `displaySize` only applies to placeholders. Extra `frames` become a looping idle animation. `Npc.holdPoint()` places held props (Aphrodite's bolt) at the art's hand point.
  - Hand-drawn SVG art for mortals (`public/assets/characters/mortals/`) and buildings (`public/assets/buildings/`) is listed in `game/graphics/propArt.ts` (`PROP_ART`) and loaded by `GameplayScene.preload()` under the placeholder's own texture key, at the placeholder's proportions (x2 where scenes stretch it, x1 where they show it at natural size). Positions, display sizes and collisions are unchanged; a missing file falls back to the placeholder.
  - Painted backgrounds are in `game/graphics/backgrounds.ts` (`addBackground`): visual only, never collision. Chapter 1 (`OlympusEntrance`) uses `public/assets/backgrounds/chapter1_bg.webp`, the hub (`OlympusHub`) `olympus_hub_bg.png` and Zeus's palace (`ZeusPalace`, and `OlympusBetrayal` with a faint lavender tint) `zeus_palace_bg.webp`, each scaled uniformly with the painting's `floorEdgeY` (a line inside the painted path or walkway, so paving shows under the feet) on the ground line and a 0.1 parallax (the file's real size is read, so `floorEdgeY` is relative to the documented height). The scene's placeholder backdrop (sky, clouds, columns, palace wall) is drawn only if its painting fails to load; Athena's library and the palace vault are always drawn over the painting. With a painting loaded, Chapter 1, the hub, Ares's arena (`ares_arena_bg.svg`) and both palace scenes hide their ground strip (its body still collides) and draws `RUIN_COLUMNS` from `public/assets/props/column*.svg` (visual only) instead of the placeholder columns. The god sizes come from `GOD_SCALE` in `characterArt.ts`.
  - The player uses real art from `frontend/public/assets/characters/player/`, loaded by `Player.preload(scene)` in the scene's `preload()`. `PLAYER_ART` in `entities/Player.ts` holds the source-pixel measurements (feet line, collision box, source facing); `PLAYER_ANIMATIONS` maps idle/walk/jump to frame keys (all one image for now). The art faces left in the file, and `face()` moves the origin and body offset together when flipping so the collision box stays put.
  - In scene cleanup, only touch the keyboard on `SHUTDOWN`, never on `DESTROY` (the keyboard manager is already gone and throwing there leaves a second Phaser instance alive under StrictMode).
  - Chapter 3 (`ZeusPalace`, `story/chapter3.ts`, `story/chapter3Dialogue.ts`): the flags, key item (`MASTER_BOLT`), reward actions, `getChapter3Objective` and the six `CHAPTER_3_STEPS` shown by the tracker all live in `chapter3.ts`. `story/access.ts` (`canEnterScene`) is checked by every `goToScene`: the palace needs all three seals AND Chapter 2 completed, so a stray `scene:start` cannot skip ahead. The statue puzzle's rules are in `puzzles/pressurePlates.ts` (E cycles each statue through fixed track positions and wraps, so nothing can get stuck; positions live in `GameState.counters`). The guard checkpoint, vault door and statue passage are full-height static `Zone` barriers independent of their art, switched off by story flags. The Warrior Badge is `seals.ares` (`hasWarriorBadge`); the guards still need the player to speak to them. `Npc.setPresent` / `interactionEnabled` show, hide and disable interactables.
  - Chapter 4 (`OlympusBetrayal` scene, `story/chapter4.ts`, `story/chapter4Dialogue.ts`): `nextChapter4Beat(state)` orders the beats after the handover (reveal, imprison, rescue, complete); the scene auto-opens each beat's scripted dialogue once and waits until it has been seen open and closed before the next. The handover is the conversation's explicit `choice` (a button), or a forced seizure on the third reply (counted, not interpreted). `isImmobilized(state)` (betrayal revealed, not yet rescued) is derived, never stored; the rescuers always land beside the player. Ownership of the bolt is only the inventory (`removeItem`); flags record events. In Chapter 4 (`chapter4Entered`) `story/conversations.ts` routes aphrodite/athena/ares/zeus to their Chapter 4 scripts. `canEnterScene` requires a completed Chapter 3 for the scene.
  - `dialogue/conversation.ts`: a step may `end` the conversation, a conversation may offer one explicit `choice`, and a `hearOut` conversation answers each reply freely (never with story actions) before its scripted `conclusion` (rendered by `DialogueBox` as a button, applied by `App.chooseDialogueOption`). Read-only dialogue boxes focus themselves (not the Close button) so stray Space/Enter cannot dismiss unread text; the log shows each new line from its start.
  - Chapter 5 (`BattleForOlympus` scene, `story/chapter5.ts`, `story/chapter5Dialogue.ts`, `puzzles/enchantmentNodes.ts`): Athena's briefing arms three enchantments that must be broken in order (out of turn resets them; progress in `GameState.counters`); a full-height barrier seals the throne room until then. Bolt ownership stays in the inventory: Chapter 4 removed it, `tryRetrieveBolt` adds it back, the "return" choice removes it again. `tryFreeZeus` needs the bolt in hand. `completeChapter5IfReady` checks every step and runs once. Aphrodite (Chapter 5 only, via `AiNpcPolicy.chapters`) and Zeus use `hearOut` conversations: AI answers each reply when available, and a scripted conclusion after three replies carries the story action, so nothing depends on how persuasive the player was.
  - Chapter completion screens open through `hooks/useCompletionScreen.ts`: only when the flag turns true while the player is in that chapter's scene, so a screen cannot reappear after scene changes or a dev shortcut.
  - Voice and conversational AI (see `docs/speech-s3.md`): `components/DialogueBox.tsx` shows `components/voice/VoiceInput.tsx` under the typed field. `App.tsx`'s `submitPlayerResponse` is the single handler for both (`method` "text" or "voice"). `getReply().freeform` marks when the script has nothing left to say; only then, and only for characters in `game/dialogue/aiPolicy.ts` (`AI_ELIGIBLE_NPCS`), `askNpc` consults the backend through `hooks/useNpcDialogue.ts` / `services/npc/*`. Scripted steps carry all story actions, AI replies are informational, and `AI_ACTION_POLICY` is empty (deny-by-default). Each dialogue has a unique `session.id`; replies for older sessions are dropped and closing cancels the request. Real failures show a note plus the scripted line, never simulated text (the simulated mode is dev-only, in the dev panel). Lines carry `source`/`method` for labelling.
  - Speaking Companion (optional, `src/companion/`, `components/companion/`): `companionStore.ts` is a standalone store (`speakingCompanion`, read via `hooks/useSpeakingCompanion.ts`) that never imports or touches the story state. It persists only goals, panel prefs and aggregate metrics in `localStorage` (`hackprinceton.speakingCompanion.v1`); the latest turn and its feedback are in memory only, and transcripts/audio are never stored. `submitPlayerResponse` calls `recordVoiceTurn(response, {npcName, npcLine})` for accepted voice replies only; it returns at once and fetches feedback in the background (`services/feedback/feedbackClient.ts` → `POST /speaking/feedback`), deduplicated per response object, latest turn wins. `PlayerResponse.durationMs` is the recorder's real elapsed time, set only for real recordings (`components/voice/confirmedResponse.ts`), never for typed text or the dev sample; `companion/metrics.ts` validates it and computes approximate WPM from the confirmed transcript's word count. Pacing is measured locally and never sent to the model. `GoalPicker` (onboarding and goal editing) takes the shared input lock with overlay id `speaking-companion-goals` (re-announced on `scene:ready`); the panel is non-modal, keeps its keystrokes from Phaser, blurs after mouse clicks and on Escape so WASD returns to the game, and narrows the dialogue box while open (`.game-shell.companion-open`). Browser tests that predate it must mark onboarding done in `localStorage` first.
- `backend/`: FastAPI (see `backend/README.md`). `main.py` is the thin app (`create_app`), `speech.py` does `POST /transcribe` (validates the recording, calls an OpenAI-compatible transcription API), `npc_dialogue.py` does `POST /npc/dialogue` (prompt building, provider call, reply filtering), `speaking_feedback.py` does `POST /speaking/feedback` (goal-shaped, JSON-validated transcript feedback using the dialogue provider; never pronunciation, accent, fluency or scores; pacing is never sent), `npc_personas.py` holds the eight conversational characters and the allowlist, `story_knowledge.py` holds chapter- and progress-gated facts (locked facts are never sent to the model), `provider.py`/`config.py`/`errors.py` are shared plumbing. `proposedAction` is always `null`: the backend only produces dialogue; scripted frontend actions decide progression. `embeddings.py` is still a stub. `ml/` is the offline ASR benchmark (`python -m ml.benchmark`, dry run unless `--run`; see `backend/ml/README.md`); it reuses `speech.transcribe` and is never imported by `main.py`. `ml/local_asr.py` + `python -m ml.local_benchmark` run an unmodified, commit-pinned local Whisper (transformers + PyTorch, MPS or CPU, weights in git-ignored `ml/models/`) through the same scoring; its deps are in `requirements-ml.txt` and torch is imported lazily, so the server never needs it. `ml/adaptation/` (M4, experimental) trains a per-speaker LoRA adapter on that frozen checkpoint (`python -m ml.adaptation.train`, dev split only, sentence-disjoint split) and compares base vs adapter through the same transcriber and scoring (`python -m ml.adaptation.compare`); adapters go to git-ignored `ml/checkpoints/`.
- `Test.py` at the root is a leftover placeholder.
